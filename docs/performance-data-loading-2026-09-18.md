# 表示高速化 第2段階：データ取得の待ちを減らす

検証日：2026-09-18（JST）。最終ビルド・比較確認：同日16:49頃。

## 結果

検索・マイページ・応募一覧の読み取り経路を変更した。
前段の測定で残った「データが届くまでの待ち」のうち、コードで再現できた
不要な待ち・重複取得・応答順の競合を対象にした。

本番端末での短縮秒数は今回測っていない。全画面の瞬間表示は未達・未検証のまま。

| 同じ条件での比較 | 変更前 | 変更後 |
| --- | --- | --- |
| 同じ利用者スコープで公開求人一覧を同時取得 | REST 2本 | REST 1本を共有 |
| 農家のマイページを開いた時の、非表示の働き手入口の取得 | 5本 | 0本 |
| プロフィールが届き、本人の実績集計がまだ未応答 | 名前は未更新 | 名前を表示 |
| 応募・求人が届き、プロフィール充足確認／返答傾向がまだ未応答 | 一覧は読み込み表示 | 一覧を表示 |
| 新しい再取得の後に古い応募・検索応答が到着 | 古い内容に戻る | 新しい内容を維持 |
| 求人詳細の取得失敗 | 手元の求人情報を空で上書き | 手元の求人情報を維持 |

通信本数は該当処理だけの数であり、画面全体の通信が0本になるという意味ではない。
重複抑止は取得中のリクエストだけ。更新通知では別の新しい取得を開始し、
完了済みの応答を最新データとして使い回さない。

## 改修箇所

- `src/components/ProfileHub.jsx`：プロフィール・緊急連絡先の登録有無・本人の実績を、
  それぞれ応答が届いた時点で反映する。応募件数は応募と評価の両方が成功した時に更新。
  農家の面・働き手の下位ページでは、非表示の働き手入口の5取得を行わない。
  役割切替・利用者変更・アンマウント後の古い応答は反映しない。
- `src/components/WorkerApplications.jsx`：プロフィールの充足確認と返答傾向を
  一覧表示の待機条件から外した。評価は操作ボタンの判定に必要なため引き続き待つ。
  仮応募のプロフィール確認が未応答なら「必須項目がそろっている」と断定しない。
  求人取得失敗時の既存情報保持、古い再取得・アンマウント後の応答の破棄も追加。
- `src/lib/searchJobs.js`：同じスコープで重なった一覧取得を共有。
  更新通知では既存の取得と分離し、失敗後・完了後は再取得できる。
  遅れた入口の先読みは、既に検索本体が更新したキャッシュを上書きしない。
- `src/components/JobSearchMapView.jsx`：更新・利用者変更・離脱で無効になった
  一覧の応答は表示にもキャッシュにも反映しない。

今回の対象は既存データの読み取りと表示。DBスキーマ、RLS、保存API、認証設定は変更していない。
問い合わせ先・取得列・本人IDの絞り込みは維持した。実アカウントへのログイン、メール送信、
本番DBへのテスト書き込みは行っていない。

## 検証

比較元は [bf31106a](https://github.com/Fukui-nano-o1/chitose-bank/commit/bf31106af0b320e095a40305d593efd41b08fcb1)。
隔離したReact + JSDOM環境で実際の3コンポーネントと取得モジュールを読み込み、
Supabaseの応答順・エラーを制御した。子コンポーネントの見た目と通信はスタブ化。
実ネットワークは拒否し、DBへの書き込み操作が呼ばれた場合も失敗させている。

変更前17シナリオで既存の挙動を確認し、変更後19シナリオで以下を確認した。
変更前の確認には、不具合が再現することの確認を含む。

1. 実績集計が未応答でも、届いたプロフィールの名前をDOMに表示。
2. 農家の面で非表示の働き手入口の取得は0本（変更前5本）。
3. 評価取得失敗時は、既知の応募件数を保持。
4. 役割を切り替えた後の古いプロフィール応答を無視。
5. セッションの利用者と表示対象が違う場合はプロフィール取得を開始しない。
6. プロフィール充足確認が未応答でも、応募と求人をDOMに表示。
7. 未応答の充足確認を「必須項目がそろった」と表示しない。
8. 農家の返答傾向が未応答でも、応募と求人をDOMに表示。
9. 応募取得の本人IDによる絞り込みを維持。
10. 求人取得失敗時に、既存の求人詳細を保持。
11. 古い応募取得が、新しい再取得結果を上書きしない。
12. 応募画面を閉じた後の応答が、消去済みキャッシュを復活させない。
13. 同時に重なった公開一覧取得は1本（変更前2本）。
14. 失敗後・完了後は新しい応答を再取得。
15. 異なる利用者スコープでは取得中のリクエストを共有しない。
16. 古い取得の完了が、新しい取得中リクエストの共有状態を消さない。
17. 遅れた入口の先読みが、新しい一覧キャッシュを戻さない。
18. 検索コンポーネントが、新しい再取得の後に来た古い応答を無視。
19. 検索画面を閉じた後の応答が、消去済みキャッシュを復活させない。

`npm run build` 成功。ESLintは0 errors / 22 warnings（変更前と同数）。
差分の検査と、修正対象のソース反映確認も完了。

## 残っている確認

- 実際にログインした端末での、操作開始から内容表示までの秒数。
- カレンダー・チャット・管理画面の本番API待ち時間と画面操作の確認。
- 保存確定から別画面への反映、および既存PWAの更新反映時間。
- 初回検索のAPI応答・画像転送・描画の時間内訳。

この検証だけから現在のSupabaseサーバーを遅延原因と断定しない。
前段のPageSpeed測定値も今回の本番実測値として再掲しない。
認証が必要な実機検証では、`CLAUDE.md` の本人ログイン規則に従う。
