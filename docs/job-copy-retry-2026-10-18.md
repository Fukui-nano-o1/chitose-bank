# 求人コピーの再送（A07）

コピー操作を `copyJobRecord.js`、画面遷移を既存 `copyJobFlow.js`、コピー内容を既存SQL `copy_job(integer)` に分担する。すべての画面の入口は共有フローを通す。未使用の旧APIエクスポートは削除する。

送信前にIndexedDBの利用者・コピー元別の記録を作る。readwriteトランザクション内のget-or-createで、同じ端末の別タブも同じ未確認操作IDを使用する。書込が確定しなければRPCを始めない。日付指定の引継ぎも操作記録へ保持し、不明な結果の再試行で別の日付へ差し替えない。

`copy_my_job_once` は本人IDと操作IDを受け取り、内部関数が既存のコピーとprivate台帳への追記を同時に確定する。記録失敗なら求人INSERTやトリガーの変更も全取消。同じ操作は新しい下書きを追加せず、既存のコピー先を返す。コピー先が編集済みなら最新行を開き、以前の日付指定を重ねない。削除済みならそれを伝え、勝手に再作成しない。既存の入力引継ぎ・日程リセット・動画再同意方針は維持する。

編集画面への引継ぎに成功した後で端末の操作を片付ける。引継ぎに失敗した場合も同じ操作を再確認できる。端末の確認記録を削除できなければ、次のコピーは同じコピー先を再確認する。端末データそのものをユーザーが削除した場合の操作ID復元は未対応。

台帳は直接アクセスを禁止する。公開関数はinvoker、内部関数は固定search_path・本人チェック付きdefiner。旧 `copy_job` の外部実行は新フロント配信確認後に閉じる。新旧の混在中も、コピーの列規則を別実装にはしない。

検証は実SQLの同一操作再送・編集済み/削除済み・台帳拒否ロールバック・本人/匿名拒否と、共通コピー処理・実画面遷移コード。UI試験の端末保管はテスト用アダプターを用いるため、実ブラウザのIndexedDB永続化や端末強制終了まで試験したという意味ではない。2接続の同時SQL負荷試験、本番の求人作成試験は行わない。
