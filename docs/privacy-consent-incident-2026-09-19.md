## 再現と変更

旧通信処理とインストール済みSupabase SDKを使い、同意UPDATEに本文が空ストリームの204応答を与えると、1回の送信後に `TypeError: Response constructor: Invalid response status code 204`、status 0になった。共通処理の修正は先行する `d9ddf76` に含まれる（求人保存の障害記録を参照）。

初回の同意保存修正（後述の端末保存対応で保存窓口をRPCへ変更）:

1. UPDATEに本人の `agreed_privacy_version` だけを返させ、保存された版数が一致した場合のみ完了する。0件・版数不一致で同意済み扱いにしない。
2. 応答が届かなかったときは、書き込みを再送せず本人の同意版数を1回照合する。照合期限は6秒。書き込み・照合のSDK自動再試行は無効。
3. サーバー障害、応答不明、認証、権限の表示を分ける。回線が原因と断定しない。
4. 連打を防ぎ、例外時も保存中表示を解除する。
5. 失敗時は既存の `app_errors` に固定の操作名・エラーコード・利用者向け文言を送信する。生のDBエラー、同意者のID、氏名、住所、認証情報を追加しない。記録の完了は画面復帰を待たせない。DB停止中は障害記録も保存できない限界がある。

RLS、同意本文、版数、本人の実データには変更を加えていない。

## 通信が途切れても作業を続ける対応

利用者から「通信エラーでも次へ進めるよう実装」の指示を受け、同意と求人下書きの保存を変更した。

- 同意操作（本人ID・版数・端末での操作日時）を端末に保存し、応答待ちの間も公開求人の閲覧・本人の下書き作成へ進む。個別の連絡先・応募・掲載はサーバーの同意確認後に開く。
- 同意の保存窓口は `save_my_privacy_consent`。サーバーの現行版数を照合し、同じ版は再更新しない。旧版のタブによる巻き戻しを拒否する。本人のRLSは維持する。
- `app_settings` はRLS有効・SELECTポリシーなしのため、認証済み利用者も直接は読めない。`current_privacy_version` は現行版数1項目だけを返す読み取り窓口とし、設定表の権限は変更しない。
- 新規・編集・コピーのフォームをアカウントと作業IDで分離して端末保存する。入力後800msの待ち時間を廃止し、入力更新後に保存する。保存領域が使えないときは保存済みと表示しない。
- 「保存して終了」は端末への保存と送信待ちの記録で閉じる。「この端末の下書き」から再開できる。新規の入口は以前の下書きを流用しない。
- オンライン復帰・フォーカス・画面再表示・再起動時に再送する。通信不調には待ち時間を延ばして再試行。認証、権限、競合、入力条件の拒否を無限再送しない。
- 同じ求人UUIDを再利用し、DBの行ロック下で読込時の内容と比較する。応答だけ失われた場合は保存済み内容と照合し、重複作成を防ぐ。別の更新と競合したら自動反映を止め、フォームを端末に残す。
- 公開中の変更は既存の `update_my_open_job` を通し、応募者がいる場合の拒否と掲載時の検査を維持する。新しい保存関数から公開状態へ直接変更しない。
- 掲載は下書きの保存確認後に既存の掲載RPCを呼ぶ。通信不調時に掲載・応募・採用が完了したとは表示しない。応募・採用・画像アップロードの自動再送はこの変更の対象外。

検証: 必須61テスト成功、ビルド成功、ESLint 0エラー（既存20警告）。実SDKでの応答断、Postgres実行環境でのRLS・重複・競合・公開中の応募者拒否、実Reactコンポーネントでの同意から待機画面・入力直後の保存・再読み込み・編集/コピー復元・再接続・掲載完了を含む。本番利用者の同意や求人を代行操作する検証は行わない。
