# 掲載と確認記録の原子的保存

確認日：2026-10-16（日本時間）。PR #9の後続。対象は求人作成フローの掲載・再提出。main・本番DB・本番デプロイは未変更。

## 原因と変更

旧経路は `publish_my_job` の成功後、別のHTTP通信で `job_publish_checks` をINSERTしていた。後者のエラーを握り潰し、通常利用者には掲載完了を表示して端末下書きを削除していた。さらに、応答紛失時は求人が `open` なら確認記録なしでも成功と扱っていた。

実際のLandingFlow＋Supabaseクライアントを動かす試験で記録保存だけを失敗させ、修正前に「掲載完了」となることを再現した。

新経路は1回の `publish_my_job_with_check` RPCに統一する。

| 保管対象 | 確定する内容 | 失敗時 |
|---|---|---|
| `public.jobs` | 既存の公開条件を通過した掲載／修正依頼中の再提出 | 同じ処理内の記録が失敗した場合も更新を取り消す |
| `public.job_publish_checks` | 操作ID、本人、求人番号、提示した確認文言、同意時刻 | 掲載だけ成功した状態を残さない。過去の追記専用記録は変更しない |
| `private.job_publication_requests` | 操作ID、固定した依頼内容、確認記録ID、掲載確定時の比較元 | 台帳の保存失敗も、掲載と確認記録の両方を取り消す |

3件の書き込みはPL/pgSQLの同じ例外ブロック内で実行する。例外時はそのブロック全体をロールバックし、`ok:false / publication_rejected / SQLSTATE` を返す。DB内で確実に取り消した拒否と、通信断で結果が不明な状態を区別する。画面はどちらも完了にせず、理由コードを診断記録へ送る。入力・確認文言などの本文は診断ログへ送らない。

## 責務と再試行

| ファイル | 責務 |
|---|---|
| `src/lib/deviceDrafts.js` | 通信前の操作ID・入力・文言・時刻の固定保存、応答照合、未反映入力の保持 |
| `src/features/jobs/create/jobCreateApi.js` | 新RPCへの唯一の送信口。掲載と記録の分離送信・旧RPCへのフォールバックを廃止 |
| `src/features/jobs/create/LandingFlow.jsx` | 未確定と拒否の案内、同じ操作の再確認、完全な確認後だけ完了表示 |
| `src/components/DeviceDrafts.jsx` | 「掲載結果の確認待ち」の表示と再開導線 |
| `supabase/migrations/20261018142043_atomic_job_publish_check.sql` | 原子的保存・本人確認・競合拒否・重複防止・実行権限 |

- 端末保存に失敗した場合、掲載RPCを送らない。
- 応答不明時は `publishing` として操作を残す。確認前の下書き再同期・比較元差し替え・コピーを止める。再読込後も同じID・文言・時刻で照合する。
- 再送は既存の操作台帳を返す。再掲載、確認記録、DB内の通知処理を重複実行しない。DBセッションの時差が変わっても同じ操作と判断できるようUTCで正規化する。
- 依頼ID・確認記録ID・求人ID・求人番号・所有者・掲載時の比較元が確認できなければ入力を削除しない。`open`という状態だけは成功の根拠にしない。
- 確認待ち中に追加入力した場合は端末に残す。次の保存の比較元は「掲載が確定した時点の入力」。別端末の後続変更を再取得して無条件に比較元へ採用しない。
- 照合時点で終了・非公開になっていたら再掲載せず、その状態を案内する。
- 明確なDB拒否の場合は操作を解除して入力を保持し、修正後に新しい操作を開始できるようにする。

## 安全条件

Supabaseの安全手順とSQL設計ガイドに沿い、公開関数は `SECURITY INVOKER`、権限が必要な実装は `private` 内の `SECURITY DEFINER` とする。固定 `search_path`、本人限定、操作IDと求人IDのトランザクションロック、求人行ロックを使用する。操作台帳はRLSを有効にし、一般利用者・匿名からの直接アクセスを禁止する。

既存の `publish_my_job` は内部利用して、停止アカウント・修正依頼の審査待ち・公開条件のトリガーを維持する。外部からの旧RPC実行権限は閉じ、分離保存へ戻る抜け道を残さない。現在のプライバシー同意版と同期後の入力スナップショットも照合する。

公開中の内容編集・管理者の公開操作など、今回の掲載確認フロー以外の経路は変更していない。既存の確認記録欠落を推測で補完しない。過去の欠落調査・本人への再確認は別途必要。

## 検証

- ローカルPostgreSQL（PGlite）に既存の掲載関数・確認記録テーブルの移行SQLと新移行SQLを適用。実際のINSERTトリガーで確認記録／操作台帳の失敗をそれぞれ注入し、求人の状態・記録数・DB内副作用が全て元に戻ることを確認。
- 通常掲載、修正依頼中の `pending`、保存後の応答紛失、同じIDの再送、文言／時刻／入力を変えたID再利用の拒否、未ログイン・別人・同意不一致・停止アカウント・古い入力の拒否を確認。
- 同じ比較元を持つ2端末の操作を順に交差させ、先の掲載後に後の掲載を拒否。行ロック実装は点検済みだが、複数DB接続の真の同時実行試験とは区別する。
- UTC／日本時間／UTC−3で操作の再照合を確認。台帳の書換え・削除拒否、旧RPCの実行拒否、操作台帳の直接参照拒否も検査。
- 実React画面＋実Supabaseクライアント＋模擬通信で、記録失敗時に完了しないこと、再試行、応答紛失後の再読込、誤った確認記録ID、追加編集の保持、終了済み求人の再掲載防止を確認。
