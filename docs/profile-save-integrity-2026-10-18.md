# プロフィール入力の競合・読込失敗対策（A03 / A04）

基点: main `eeed705216d1402fc242392e99efadabda6a367b`。確認日: 2026-10-18。
対象: 雇い手・働き手プロフィール、経験、保険準備の2画面、緊急連絡先。画像はPR #13の保存経路を維持する。

## 保存の契約

| 窓口 | 責務 |
| --- | --- |
| `profileInput.js` | 画面の項目と保存列の対応。関係しない項目は送らない。自由記述は従来の公開トリガーを通す |
| `profileRecord.js` | 読込成功／行なし／失敗の区別、本人確認、条件付き保存、応答紛失時の再照合 |
| `save_my_profile_fields` | RLSに従う本人行への更新。比較元の各値と変更を同じSQL文で照合・反映。初回はINSERTし、同時作成を上書きしない |
| 6つの編集画面 | 読込失敗時は再読込を案内し保存しない。保存中は二重送信と追加入力を止め、失敗・競合時は入力を保持する |

比較元と入力はRPCのPOST本文で送る。長い自由記述やJSONをURLフィルターへ載せない。JSONは配列の順序・全内容を含む一致を要求し、包含判定は使わない。別の項目を変更した保存は両立し、同じ項目の古い保存は競合になる。画像や作業場など、別経路が管理する列はプロフィール全体の保存で巻き戻さない。

RPCは`SECURITY INVOKER`、固定search_path、テーブル・列の許可リスト、`auth.uid()`による対象固定を使用する。匿名への実行権限は付けない。既存RLS・テーブル権限・検査／公開トリガーは変更しない。ユーザー情報の入力・公開範囲を増やさない。

保存成功はDBの確定行から判定し、表示・キャッシュを更新する。応答だけ失った場合は本人の正本を再読込して入力値を照合する。照合にも失敗した場合は「確認できない」と案内し、画面の入力を消さない。永続的な操作台帳は今回追加していない。

## 検証

- 旧mainの実React画面で、読込拒否後にも入力・保存へ進める6画面を再現。修正後は保存ボタンを出さず再読込に成功すると編集を再開する。
- 共通保存処理: 同じ項目／別項目の競合、リクエスト中の更新、JSON比較、DB拒否、応答紛失と再照合失敗、初回同時作成、別アカウント／ログアウト、公開後の確定値、時刻表現、無変更保存。
- 実画面: 通常保存・保存拒否・応答紛失・読込再試行・保存中の操作抑止。競合時の入力保持と他項目の保全。
- PGliteで実migrationを実行。列の型・既定値と自由記述トリガー3つは本番カタログの読み取りから固定したfixture。本人RLS、匿名拒否、制限付き委託テーブル、初回INSERT、部分更新、完全JSON比較、長文、列制限、公開処理とエラー時のロールバックを検証。
- DB試験のNG判定・メール送信先はローカルの代替関数。メールを送らず、既存検査関数が呼ばれたことを確認する。全本番トリガーを複製した試験ではない。
- 全体ビルド: 394件成功、失敗・スキップ0。ESLintはエラー0・既存警告19件。Vite/PWAの本番ビルド成功。

## 反映順序・残る境界

CI成功後、追加RPCを先に適用・権限と定義を確認し、それからフロントを反映する。旧フロントとの互換性を維持する追加変更であり、データ移行や既存行の変更は行わない。切り戻す際もRPCは残せる。

本番の利用者データへの書込試験、実機2台での通信試験は未実施。古いコードを開いた端末や、今回の窓口を使わない既存管理操作には新しい競合規則は適用されない。既存の直接更新権限は維持しているため、全書込経路の強制的な一本化は別の変更として扱う。未保存の入力はメモリ上の保持であり、ブラウザ終了後の復旧台帳は未実装。

次順位: 掲載と確認記録の一体保存（未反映PR #10）、コピー項目の欠落（A16）、委託情報（A11）、ヘルプ画像（A12）。満額支払条件（A13）は仕様判断を要する。

## 追加の本人照合（2026-10-18）

3引数RPCでは、画面のセッション確認後、HTTP送信までにログイン先が切り替わり、両者の比較値が一致すると、新アカウントの同じ項目を旧画面の入力で更新できることを実SQLで再現した。RLSは新アカウント自身の更新として許可するため、RLSだけでは編集元の利用者を識別できない。

4引数版 `save_my_profile_fields(text,jsonb,jsonb,uuid)` に編集時の利用者ID `p_owner` を必須化し、DBで `auth.uid()` と照合する。旧3引数版の外部実行権限を閉じる。4引数版もinvokerで、許可項目、比較規則、公開トリガー、RLSは維持する。旧画面では再読込が必要。実SQLによる修正前再現・修正後拒否、旧RPC拒否、共通クライアントの送信直前切替を検証する。
