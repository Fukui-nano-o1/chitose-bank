# 集合場所の詳細住所：承認条件の統一

情報開示検証の2件目。集合場所の番地・建物名を対象とし、緊急連絡先は別途対応する。

## 原因と変更

`job_details_for_party` は応募履歴がある人に `work_address` を無条件で返していた。専用の `job_meeting_place` は承認済みの応募状態を要求しており、経路ごとに条件が異なっていた。

今回、`private.can_read_meeting_address` に次の条件を定義し、詳細RPCと `jobs_public.work_address` に適用した。

- 対象求人の募集者本人、管理者、または対象求人に `approved / meeting / interview / contracted / working / completed` の応募を持つ本人だけに返す。
- `applied`、拒否・取消・失効、未知の状態、無関係な会員、匿名には詳細住所を返さない。返却値はNULL。
- 求人の存在・概要の閲覧範囲は維持する。`jobs_public` の既存 `security_invoker=true` と元テーブルのRLSを維持した。現状の本番では無関係な利用者への一覧返却は元から制限されており、そこで追加の漏れを再現したわけではない。
- 番地の有無を示す `has_work_address` は維持する。画面では未開示時に「番地・建物名は承認後に表示」と案内する。
- 既存の契約スナップショット、求人の入力内容、応募状態は書き換えない。専用の集合場所RPCの条件は変更しない。

## 検証

- 架空データを使ったPostgreSQL検証20件成功。元の詳細RPCによる漏れを再現し、修正後の応募中・承認後・拒否・取消・失効・別利用者・所有者・管理者を検証した。
- 一覧については現行の行制限が維持されることを確認したうえで、テストDBだけに閲覧可能な行を用意し、列の承認条件と値による絞り込みでも詳細住所が漏れないことを検証した。
- 全体の回帰テスト712件成功。ESLintはエラー0件・既存警告19件、Vite/PWA本番ビルド成功。その後のSQLオプション明示変更も専用20件を再実行して成功。

本変更は集合場所の住所項目の取得条件を修正するもの。募集者情報として公開する住所、自由記述に書かれた場所、過去に取得・保存された情報の回収は対象外。
