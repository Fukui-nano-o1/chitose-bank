# 画面ファイル読み込み失敗の診断（2026-10-26）

## 目的

10月26日00:26:59 JSTの `#err:960b3551` はCSS取得失敗の文言だけを保持し、HTTP応答を保存していなかった。この過去の原因は復元できない。次回から、画面ファイルの不具合を証拠に沿って判断できるようにする。

## 記録と表示

- 既存 `app_errors.metadata.asset_load` を使う。既存の管理者限定閲覧・1年保持・送信間引きを維持する。
- 読み込めなかった同一サイトのハッシュ付きJS/CSS名、実行中の入口ファイル名、観測時刻、接続状態の申告、Service Workerの関与を記録する。
- Resource Timingに残っている元の通信のHTTP応答と所要時間を、失敗後のHEADによる再確認と区別する。
- HTTP 0・未対応・取得不能は「不明」。再確認時200は「その時点の取得成功」であり、元の通信成功・画面復旧・安全性の証明ではない。
- 詳細展開時に最新1件のmetadataを取得し、管理画面とコピー報告文に同じ説明を表示する。
- 先読み失敗も記録するが、操作中の画面は再読込しない。先読み失敗は表示停止の証明ではない。
- 自動再読込前にも失敗を記録する。「実行予定」を記録するだけで、画面全体の復旧成功を推定しない。

## 負担と制限

再確認は同一サイトの `/assets/` 配下のハッシュ付きJS/CSS限定。クエリ・フラグメント・外部URL・APIは対象外。HEAD、認証情報なし、no-store、リダイレクト拒否。1ページで異なる対象最大3件、同じ対象の再発は観測日時付きで最初の結果を共有する。1件最大1.2秒。診断送信の待機は最大2秒で切り上げ、従来の再読込へ進む。診断の失敗で無限再読込や追加のエラー記録を起こさない。

初期のJSそのものが動かない場合、端末が閉じた場合、送信できなかった場合は記録できない。ブラウザによって元のHTTP応答は取得できない。CSP、通信断、利用者による中断などを未確認のまま断定しない。

## セキュリティの判断

この情報はブラウザ申告であり、攻撃判定や認証には使用しない。Bingbot/Googlebotの名乗りから本人性を断定しない。本物のBotかの確認には、配信側の接続元IPとMicrosoft/Googleの検証方法によるサーバー側検証が別途必要。本変更ではIPの追加保存・Botの許可/遮断・DNS検証API・権限変更は導入しない。
