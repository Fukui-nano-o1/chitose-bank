# 利用状況の計測（2026年9月23日）

管理 → その他 → 利用状況。過去7日／30日の画面表示、訪問のきっかけ、応募送信・掲載／更新・労働条件通知書PDFの開始と結果を確認する。

## 利用者の選択

初期値はOFF。説明の「許可する」を押した場合だけ記録する。登録時の規約同意とは別。
マイページの設定とプライバシーページでいつでも変更できる。拒否でも全機能を利用可能。
選択は端末のlocalStorageに180日間保存し、版が変われば未選択に戻す。
保存不可・壊れた選択・期限切れでは送信しない。撤回時は待機中の記録を破棄し、処理中の送信を中止する。
すでにDBへ到着した記録を取り消す仕組みではない。新たな計測は停止し、受信済みの記録は最長30日で削除する。

## 計測仕様

- Airbnbが公開している「利用状況を把握し改善する」目的を参考に、千歳用の固定イベントを実装した。Airbnb内部のコード・計測基盤を再現したものではない。
- 生のURL、自由記述、氏名、会員番号、求人番号、正確な位置、画面録画、キー入力、広告タグは含めない。
- 画面は固定カテゴリ、流入は指定なし／Instagram／QR／LINE／その他に変換する。`?src=insta`等は許可後に参照し、任意のクエリ文字列は送らない。
- ランダムな訪問IDはメモリだけに保持。再読み込みまたは30分無操作で更新する。認証IDと結び付ける列は作らない。完全な匿名加工情報という法的評価をするものではない。
- 通常のSupabase通信を使うため、IPアドレス等の通信情報・ログイン時の認証情報は通信先に届く。計測テーブルには保存しない。新たな広告・解析事業者への転送は追加していない。
- `product_events`への書き込みは許可列・固定値・同意版・同意時刻の制約で検証。非管理者は読み取り不可。管理画面はRLSを守るsecurity invokerの集計RPCだけを読む。
- 2秒間隔、最大20件ずつ送信。通信期限も2秒で、応募・保存用の通信枠は使わない。未送信はメモリ40件まで、1訪問500件まで。再送・端末へのイベント保存をしない。通信が途切れた時は記録が失われる。
- `purge-product-events`が毎日02:17 UTCに29日超の記録を削除する。削除ジョブが正常に動くことで最長30日以内を守る。運用時はcronの失敗を確認する。
- 旧`page_events`の未ログインINSERTポリシーは削除する。古いクライアントからの常時計測もDBで拒否。運営者自身の動作確認用記録は継続。

## 数字の見方

1. 失敗のある操作を試して確認する。採用結果や求人件数ではなく、送信・作成の試行回数。
2. 20秒以上の処理が増えたら通信と処理を調べる。結果が返った操作だけが対象。
3. 結果未記録は、開始から30分経過して成功も失敗も届いていない操作。画面を閉じた、通信が切れた、同意を撤回した場合もある。離脱や失敗の確定値として扱わない。
4. PDFの成功は保存呼び出しが完了したこと。端末側で実際にファイルを保存したかは検証できない。
5. 許可者だけの部分的な集計。訪問数は人数ではない。運営者の操作は除外。利用者の評価・採用判断には使わない。

## 配備と確認

1. `optional_product_analytics`マイグレーションを適用。新テーブル・権限・集計RPC・削除ジョブを確認。
2. フロントを配備。プライバシー本文と`PRIVACY_VERSION`の新しい版を同時に公開。
3. 公開完了後、`supabase/operations/activate_optional_analytics_privacy.sql`を実行して`app_settings.privacy_version`を`v4.6-2026-09`へ更新し、登録時・再同意・下書き同期の版を一致させる。
4. 同意前／拒否中のINSERTなし、許可後の固定イベント、撤回後の待機破棄、非管理者の読み取り不可、管理者の集計、30日以内の削除を確認する。
