# 勤怠報告・異議申立ての再送重複防止（A09）

対象は DayReportSheet の日別報告と WorkerApplications の欠勤記録への異議申立て。従来は送信ごとに UUID を採番して INSERT していたため、応答紛失後の再送で記録・相手への通知・運営への連絡が重複した。

## 保管と送信

- `operationStore.js`: IndexedDB の読書きトランザクションで操作の取得／作成を直列化。コピー処理の既存保管実装を共用化した。求人コピーのDB名・キー・形式は変更しない。
- `attendanceRecord.js`: 所有者・応募・日付・用途ごとの操作IDと元の入力全文を送信前に保管する。読み込み／書き込みが失敗した場合は送信しない。応答が不明なら同じIDと元の内容で照合する。
- `useAttendanceRecord.js`: 開き直した画面に未確認の内容を復元する。送信中は入力を固定し、同期的なロックで二重開始を防ぐ。所有者・対象が変わった後の応答で別の画面を完了させない。
- 日別報告と異議申立ては同じ保存部品を使用する。未使用の直接INSERT APIは削除した。

## DBの確定

`record_my_attendance_once(p_owner,p_event_id,p_input)` は SECURITY INVOKER。所有者一致を確認し、既存の当事者RLS・停止アカウント判定・通知トリガーをそのまま使用する。イベントIDのトランザクションロックを取り、既存行が本人の同じ内容ならその行を返す。内容や記録者が異なるIDの流用は拒否する。

初回だけINSERTし、通知トリガーを実行する。失敗時は記録と同一トランザクション内の通知を取り消す。INSERTが0件でも成功と扱わない。再送ではINSERTしないので通知トリガーも再実行しない。日付、理由、内訳のnullを含めて照合する。

確定した結果が画面に渡った後に端末の未確認記録を片付ける。片付けに失敗しても同じ操作を再確認できる。応答不明の間に入力が変わった場合、前回分の確定と変更分の未送信を区別し、変更した内容を保存済みと表示しない。

## 検証・境界

- PGlite: 本番から読んだ列・制約・当事者RLS・勤怠通知／停止判定トリガーを使い、通常保存、同一IDの再送、入力差替え拒否、通知失敗時の全取消、異議申立て、非当事者・匿名・停止・別所有者・不正入力・0件保存を確認。メール・運営通知の送信先は試験用テーブルへ置き換え、実際には送信しない。
- 共通保存処理: 応答紛失、再読込復元、同時開始、所有者切替、端末保存失敗、不一致の応答、片付け失敗を試験。
- 実React部品: 日別／異議の正常送信、二重押し、応答紛失後の再表示、読込失敗、拒否、変更後入力の未送信表示を試験。
- 端末保管は試験アダプター。実ブラウザの強制終了・端末記憶域消去・実2端末の同時負荷は未検証。ブラウザ保存を消去すれば同じ操作IDを復元できない。独立した端末で意図的に新しい報告を行うことまで禁止する業務上の一意制約は追加していない。
- 外部メールの到達・再配信保証は既存処理のまま。既存のメール例外処理も変更しない。通常保存した後の新しい報告は別操作として記録できる。作業全体の出欠・完了の規則は変更しない。

## 反映

1. 新規RPCのmigrationを適用し、所有者検査・固定search_path・実行権限を照合。
2. CI成功後にマージ。wwwの配信コードに新RPCと端末保管処理が含まれることを確認。
3. 本番の実利用者の記録・通知は作成せず、実SQLの障害再現は隔離した試験DBで行う。
