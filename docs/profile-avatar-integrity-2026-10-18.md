# プロフィール画像の保存保護（A01 / A02）

確認日: 2026-10-18。基点: main `b17b6ef9a838afd554636f5391b44b19b6a3308b`。
対象: 雇い手・働き手プロフィールの画像変更／削除。
発見元: [入力保存経路監査 PR #11](https://github.com/Fukui-nano-o1/chitose-bank/pull/11)。

## 修正

旧実装はフォルダー内の画像を先に削除し、同じ `avatar.jpg` へ上書きしていた。新画像の保存失敗で旧画像を失い、DBエラー時にも画面だけ成功へ進んでいた。

| ファイル | 責務 |
| --- | --- |
| `src/lib/avatarUpload.js` | 操作ごとに異なるキーへ上書き禁止で保存。応答紛失時は同じキーを再試行し、取得した画像のバイト列が今回の画像と一致した場合だけ保存を確認 |
| `src/lib/profileAvatar.js` | 本人・保存先・現在値を確認し、画像URLと更新時刻を条件にDB参照を変更。DB応答紛失時は新しいURLとの一致を再照合。確定後に旧ファイル1件のみを削除 |
| 2つのプロフィール編集画面 | 変換・選択と結果表示。処理中の再操作をrefで拒否。確認済みURLだけを画面・キャッシュへ反映。「完了」で他のプロフィール項目を書き戻さない |

削除もDB参照を空にする処理が先で、確定できなければStorageを削除しない。他プロフィールにも参照される画像・本人フォルダー外の画像は削除しない。フォルダー一括削除は廃止した。

既存行は条件付きUPDATE、新規行はINSERTを使う。別端末での画像変更・更新時刻の変更・初回行作成と競合した場合、全体upsertによる上書きを行わない。

## 検証

- 本番の列・既定値・本人RLS・Storageパス制約を読み取りで確認した。DB変更／権限変更／依存パッケージ変更はない。
- 共通処理の22試験: 通常保存／削除、Storage・DB・読込拒否、同サイズでも異なる画像の拒否、保存後の応答紛失、照合も失敗した場合、同一比較元からの2編集者、更新時刻の競合、初回作成競合、匿名・別アカウント・途中ログアウト、清掃失敗、共有参照の保護。
- 実React画面をViteでビルドしてJSDOMで操作: 16ケース＋親テストの17件成功。旧mainの実ソースに同じ失敗操作を与えると、雇い手・働き手各3ケース（合計6ケース、親を含む7件）が失敗した。
- `TZ=Asia/Tokyo npm run build`: 329件成功、失敗・スキップ0件。本番用バンドル生成成功。Lintエラー0件、既存部分の警告19件。

試験ではStorage・DBを模擬し、実際の画像変換部分にはテスト用画像を与えた。本番の利用者画像・入力情報を変更していない。実機2台や本番認証セッションを使った画像保存は未実施。

## 残る境界と次順位

- 保存結果不明時は新旧両方のファイルを保持する。DBの正本は再読込で確認できるが、未参照ファイルの自動回収・操作履歴の永続化は未実装。清掃失敗は保存成功と区別して案内する。
- プロフィール全体の全項目upsertと読込失敗後の空欄保存（A03/A04）は次順位。今回、画像欄の保存からは切り離したが、他の項目全体を修正済みとは扱わない。
- 古いコードを開いたままの端末には再読込が必要。旧 `farmers` 用の未使用プロフィール画面と、管理者ヘルプ画像（A12）は今回の対象外。
