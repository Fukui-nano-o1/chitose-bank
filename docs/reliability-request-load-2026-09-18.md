## 通信の変更

`src/lib/requestTransport.js` を追加し、既存の単一Supabaseクライアントから使う。対象はそのSupabaseプロジェクトの `/rest/v1/` に限る。

| 項目 | 動作 |
| --- | --- |
| 同時読み込み | 1クライアントあたり最大3本。既知の読み取りRPCも含む |
| 同時送信全体 | 最大4本。読み込みで全枠を埋めず、操作用に1枠を確保する |
| 待機順 | 操作を優先し、同じ種類の中では到着順。未知のRPCは操作側として扱う |
| 待機上限 | 64件。上限を超えた要求は送信せずエラーにする |
| 1回の送信の期限 | 待機開始から応答本文の受信まで15秒。期限切れは `AbortError` として返す |
| 中止された待機要求 | 待機列から取り除き、後から送信しない |
| 認証・Storage | この待機列には入れない。従来のタイムアウト経路と呼び出し元の中止信号を維持する |
| 保存・権限 | 既存のURL、HTTPメソッド、引数、認証ヘッダー、RLSに従う。保存要求の統合や独自の自動再送はしない |

同時数の制限はブラウザー内の共有クライアント単位。複数タブ・別端末・全利用者を横断した上限ではない。混雑時には読み込みを順番に待たせるため、すべてのデータ取得が同時に始まるわけではない。

変更前の `AbortSignal.timeout(15000)` は `TimeoutError` を返す。インストール済みのSupabase SDKはこれをGET等の通信失敗として最大3回再試行する。仮想時計で、15秒の試行4回と1・2・4秒の再試行待ち、合計67秒になる経路を再現した。変更後は意図した期限切れを `AbortError` とし、同じSDKで再試行せず15秒でエラーになることを確認した。

この15秒は1回の送信の上限。HTTP 503・520や通常のネットワーク失敗に対するSDK既存の再試行は残るので、すべての論理的な問い合わせが15秒以内に終わる保証ではない。根拠はインストール済み `@supabase/postgrest-js` の `PostgrestBuilder.ts` と `types/common/common.ts`。独自fetchの接続箇所は [Supabase JavaScript初期化](https://supabase.com/docs/reference/javascript/initializing) の `global.fetch` に従う（2026-09-18確認）。

応答本文まで送信枠を維持するため、REST応答は本文を受信してからSDKへ渡す。結果をキャッシュする処理ではない。SDKも元から全文を読み取って解析する経路が対象で、Storageのストリームは対象外。

通信の中止は、サーバー側のSQL実行や書き込みが必ず取り消されたことを意味しない。保存結果が不明な場合の既存の扱いを維持し、通信エラーを成功に見せる処理は追加していない。

同じFunctionインスタンスで同時に受けた監視要求は、進行中のDB問い合わせ1本を共有する。完了結果はキャッシュせず、次の監視では新しく確認する。別のFunctionインスタンス間では共有しない。GET/HEAD、正常時200、異常時503、対応外メソッド405、`no-store` は維持する。

## 検証結果

本番への負荷試験や実アカウント操作は行っていない。実際にインストールされたSupabase SDKと標準のRequest/Responseを使用し、通信だけを架空の応答へ差し替えた。

| 検証 | 変更前 | 変更後 |
| --- | --- | --- |
| 5クライアント×20読み込みの一斉開始 | 100本が同時送信 | 最大15本。同じ100件をすべて処理 |
| 15秒で応答しないGET、仮想時計 | 4回送信、合計67秒 | 1回送信、15秒でエラー |
| 読み込み集中時の保存 | 読み込みに同時数の上限なし | 読み込み3本の間に、操作用の4本目を送信 |
| 同じFunctionで監視5件 | 各要求が個別に問い合わせ | DB問い合わせ1本を共有 |
| 監視の3秒期限 | 返答は503、通信が継続し得る | 503と同時に通信の中止を要求 |

追加した `scripts/request-transport.test.mjs` と `scripts/health-capacity.test.mjs` の計19テストが成功。待機列の上限・中止・回復、応答本文が止まる場合、認証等の迂回、取得件数・単一行解析、保存引数、HTTPエラーの保持、503の既存再試行も確認した。

## 残る確認

障害が起きた時刻のPostgREST・Realtime・Postgresログと、CPU、メモリー、I/O、接続待ちを照合する必要がある。過去記録と同じ接続プール再構築なのか、現在のCompute容量不足なのか、別の障害なのかを切り分ける。今回の管理APIでは必要な指標を取得できなかった。

公式資料ではFreeのNanoとMicroはともに共有CPUで、メモリーはそれぞれ最大0.5GBと1GB。現在の当該プロジェクトのComputeサイズは直接確認できません。Freeであることだけで原因を断定したり、Microへの変更で必ず解決すると約束したりはできない。Compute変更は停止時間を伴うため、稼働情報に基づいて別途判断する。[Supabase Compute資料](https://supabase.com/docs/guides/platform/compute-and-disk)（2026-09-18確認）。

課金はOrganization単位なので、有料化の判断では同じOrganizationのNitoronも含める。今回、有料化や他プロジェクトの変更は行っていない。
