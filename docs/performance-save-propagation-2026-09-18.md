# 求人・応募・評価の保存後の反映（2026-09-18）

求人の保存・公開、応募・取消、承認・評価の成功後に、関連画面の再取得をすぐ開始するようにした。比較元は main `09e32d92428ddc084a9ba49b3386a67a3f4d5e07`。今回追加した比較検証21シナリオと、以前の改修38シナリオが通った。ビルドは0エラー・20警告で、警告数は変更前と同じ。

対象は、操作が成功した同じブラウザー内の画面更新。従来は操作元だけが変わり、関連画面がRealtimeや定期更新を待つ経路があった。前回導入した成功専用通知へ接続し、通常通知の5秒間隔制限を挟まず再取得を始める。APIの応答・描画の時間は残るため、実機の短縮秒数や全画面の瞬時表示は確認できません。

| 操作・画面 | 今回の変更 |
| --- | --- |
| 求人の下書き保存・公開中の編集・掲載 | 成功後に求人の更新を通知。掲載前の同意記録を保存する通信が遅くても、求人の再取得を開始する |
| 求人の一時非公開 | 求人と応募の両方を更新。非公開に伴う応募状態の変更も既存APIで照合する |
| 下書き削除 | 成功後に求人を更新 |
| 本応募・仮応募・それぞれの取消 | 応募を更新。既に応募済み・取消対象が存在しないという従来の正常扱いも再取得へつなぐ |
| 承認・見送り・対応記録・合意日・欠勤記録・双方の評価 | 各保存処理の成功判定後に応募を更新 |
| 採用完了 | 既存の完了演出を閉じるコールバックで、応募に加えて求人も更新。満員による状態変更を照合する |
| 検索画面の応募状態 | 応募の更新通知を受け、自分の応募・仮応募を一括で取得。選択中の求人だけの取得を重ねず、公開求人一覧も取り直さない |

成功通知にはデータを載せない。表示の内容は従来のAPIとRPCで取得する。保存の条件、送信先、送信内容、SQL、RLSは変更していない。公開中の編集・採用・承認などのサーバー側の拒否を、画面側の更新で成功扱いにすることもない。

一般の掲載は「求人を保存してから公開する」という既存の2段階処理。保存が成功し、その後の公開が拒否・通信失敗になった場合も、保存済みの最新状態を照合する。公開成功の完了画面は出さない。掲載前の同意記録の保存と、それを待ってフローを完了する順番は維持している。

表示が元に戻る競合も修正した。成功通知の時点で、求人・応募ごとの更新番号を同期的に進める。取得開始時の番号と違っていれば、古い応答を表示とキャッシュに書き戻さない。Reactの次の描画前や、短時間の通知を100msでまとめている間にも判定できる。農家の求人・応募者一覧には離脱時の後始末も追加した。

公開求人の取得を共有する仕組みも同じ更新番号を見る。保存前から続いている通信を、保存後に開いた画面が再利用しない。古い取得が終わっても新しい取得の登録を消さず、古い先読みが共有キャッシュを書き戻すことも防ぐ。保存のない通常の同時取得は引き続き共有する。

必要なデータを更新し、古い応答を無視し、取得を共有する考え方は [React公式のデータ取得と競合対策](https://react.dev/reference/react/useEffect#fetching-data-with-effects)（2026-09-18確認）を参照した。特定企業の非公開実装を再現したという意味ではない。
