# 表示速度の現状と改修順序

計測日：2026-09-18 JST（2026-09-17 UTC）。第1〜6節は初回計測・現状整理時点の記録。
その後の改修と追加計測は第7節以降に記録する。
高速化候補 `25dc5e1271a43ed1ef41962b6a82441e387e375a` はローカル保存済み、未push。

公開検索画面の初回表示には、今回の低速4G計測で LCP 7.7秒を要した。
先頭画像の取得開始が遅く、登録URLでは共通のお知らせ画像がフォームを覆っていた。
コード量の削減だけで「全画面が一瞬で操作できる」とは判定できない。

## 1. 完了条件と計測の区別

| 操作 | 暫定目標 | 何を確認するか |
| --- | --- | --- |
| 一度開いた画面への再訪 | 100ms以内 | 前回の内容が見え、主要操作を受け付ける |
| 再読み込み | 500ms以内 | 前回の内容と主要操作を復元する |
| 初めて開く画面 | 1秒以内 | 主要な内容が見え、操作できる |
| 保存ボタンを押す | 100ms以内に反応 | 受付状態を表示。保存完了の表示はサーバーの確定後 |

これらは目標であり、達成を確認した数値ではない。キャッシュ済みの表示と最新データの反映を別々に測る。
端末・OS・回線・ログイン状態・キャッシュ状態・お知らせの既読状態を固定して比較する。
低速4Gの初回訪問は別の厳しい条件として扱い、通常回線や再訪の数値に混ぜない。

測る時間は以下の4種類。

1. 画面遷移／リロード → 内容表示 → 主要操作が可能になるまで。
2. データ取得開始 → 応答 → 画面反映。サーバー待ちと描画待ちを分ける。
3. 保存操作 → サーバー確定 → 自画面・別画面への反映。
4. mainへのpush → デプロイ完了 → 既存タブが新コードを使うまで。

FCPは最初の描画、LCPは画面内で最大の画像・テキストの描画を表す。
どちらも「フォームを操作できる」「データが最新になった」ことの証明にはならない。
Lighthouseと実利用の測定を区別する考え方は [GoogleのLCP解説](https://web.dev/articles/optimize-lcp) に準拠する。

### 検索で確認できたこと

- LCP要素は最初の求人カード画像。レポートに `loading="lazy"` が記録されている。
  `src/components/JobCard.jsx` でもカード写真は一律lazyだった。
- LCP診断の取得開始待ちは2,980ms、画像の取得は1,670ms、描画待ちは70ms。
  これは診断欄のトレース値であり、シミュレーションされたLCP 7.7秒と足し合わせて説明しない。
  開始待ちのすべてがlazy属性だけに起因するかは、まだ分離できていない。
- 画像配信改善の推定削減量は262KiB。求人写真のほか、現金支払いのお知らせ画像も対象。
- CLS 0.319の診断にはフッターの移動と、寸法未指定のお知らせ画像が挙がっている。
  画像用の領域を事前に確保する修正を優先する。原因ごとの寄与は修正前後で確認する。
- フォントCSSから多数の日本語フォントへ続く依存関係がある。TBTが10msだった今回の結果から、
  最初の対処は長いJavaScript処理の削減だけに限定せず、取得順序・画像・CSSを優先する。

### 登録URLで確認できたこと

- **LCPは登録フォームではなく、`/notice-payment-cash-2026.jpg`。**
  最終スクリーンショットでも共通のお知らせが前面に出ており、背後に別のお知らせが見える。
  6.3秒を登録フォームの操作可能時間として採用しない。
- LCP診断の取得開始待ちは4,840ms、画像取得70ms、描画待ち100ms。
  検索と同様、診断欄の値とシミュレーションLCPは別に記録する。
- 描画を妨げるリクエストの推定削減時間は2,630ms。
  対象はメインCSS、Leaflet CSS、`registerSW.js`、`/fonts/fonts.css`。
  フォントCSSは転送31.8KiB、診断上940ms。推定削減時間は実際の改善時間の保証ではない。
- 次の登録計測は「お知らせ未読の初訪問」と「お知らせ既読のフォーム表示」を分ける。
  お知らせを消しただけで登録フローを高速化したとは扱わない。

## 5. 次に直す順序

1. **先頭画像の取得開始を早める。** 検索の最初に見える画像に限定してlazyを外し、優先度を付ける。
   画面外の全画像を一斉取得しない。候補コードとの比較でLCPと取得開始時刻を確認する。
   [GoogleのLCP最適化指針](https://web.dev/articles/optimize-lcp) に沿う。
2. **初回表示を妨げる共通資産を減らす。** 候補のフォントCSS変更を実測し、
   登録入口に必要のない地図CSS等の依存を確認する。案内画像は表示領域を確保してずれを抑え、
   適切な寸法・形式で軽量化する。[画像領域の確保に関するGoogleの指針](https://web.dev/articles/optimize-cls) に沿う。
3. **ログイン後の待ちを測ってから直す。** 既存キャッシュを活かし、画面ごとの内容表示・API応答・
   最新反映を区別する。過去に発生した冷間サーバー待ちが続いていれば、JS削減とは別に対処する。

最初は主要6画面（検索・登録・カレンダー・チャット・マイページ・管理）の同じ操作を各3回記録し、
中央値・最大値・失敗を残す。全画面の完了判定には、個別の詳細画面・編集画面も台帳に追加する。
本番反映前後で同じ条件を使い、読み込み表示だけが早まった場合は目標達成としない。
