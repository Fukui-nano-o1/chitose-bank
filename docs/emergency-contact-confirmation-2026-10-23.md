# 緊急連絡先の確認条件の修正

2026年10月22日の検証報告にあった、未確認の「本人」の緊急連絡先が作業中の契約相手に返る経路を修正した。

## 原因と変更

利用規約第4条6項は、初期登録された緊急連絡先を本人が内容確認・保存するまで相手方に表示しないと説明している。一方、`contract_emergency_contact` は `relation = '本人'` の場合だけ `confirmed_at` を要求していなかった。また、保存済みの氏名・電話番号が空欄の場合に `account_holders` の値で補っていた。

- 関係が「本人」である場合も含め、`confirmed_at IS NULL` なら氏名・続柄・電話番号を返さない。未登録も同様。
- 確認・保存された緊急連絡先の値だけを返し、空欄や削除済みの値を登録情報で補わない。
- 契約当事者、契約成立、作業開始済み・未終了、相手方の現行プライバシーポリシー同意という既存条件を維持する。
- `emergency_contacts` の本人限定RLS、保存API、登録時の初期値生成は変更しない。確認日時の一括補完は行わない。
- 保存画面に「本人の連絡先も内容を確認して保存するまで相手に表示されない」と明記する。
- 表示済み連絡先のモジュール共通キャッシュを廃止し、再表示時にはDBから取得する。取得中に応募や作業状態が変わった場合、以前の値を表示しない。

## 本番DBへの適用と確認

- 適用日時: 2026年10月23日15:27 JST。
- Migration: `20261023062726_emergency_contact_explicit_confirmation.sql`。
- 適用後の関数定義がテスト対象の定義と完全一致。
- 本番migration履歴とリポジトリのSQLのSHA-256が一致（前後空白を除去）: `b5e19c3d3b39f07fe2de2fbe8e74d7deef7e2b8c350211b9db4544dd4282fa84`。
- 既存14件は全件未確認のまま保持。氏名・電話番号・確認日時など利用者データへの書き込みなし。
- 実在する32応募について、読み取り専用トランザクション内で当事者双方の認証ロールを模擬した64呼び出しに連絡先なし（未契約50、作業時間外14）。無関係な利用者による32呼び出しはすべて `not_party`。
- 他人の緊急連絡先テーブルの直接取得は0件。匿名ロールの関数実行権限なし、会員の実行権限は維持。
- セキュリティアドバイザの指摘カテゴリに増加なし。既存の別件指摘を解消したという意味ではない。

## 回帰テスト

`scripts/emergency-contact-db.test.mjs` はPGlite上で修正前の本番RPCによる未確認「本人」の開示を再現してからmigrationを適用する。確認前後を両当事者から検証し、家族、未登録、空欄保存、部分的な空欄、確認取消、他人による確認拒否、同意不足、契約前、作業前後、匿名、無関係な利用者も検証する。既存の実際の保存RPCで確認・保存から開示までの経路も試す。

`scripts/emergency-contact-ui.test.mjs` は実コンポーネントを実行し、開き直しでの再取得、以前表示できた連絡先が未確認になった場合の非表示、作業終了後に返った応答の破棄、取得エラー時の非表示を検証する。既存プロフィール画面のテストにも、表示や「本人」の選択だけでは確認済みにならず、明示的な保存で初めて確認日時が保存される検証を追加した。

`npm run build` 成功: 全740テスト成功、ESLintエラー0（既存警告19）、Vite/PWAビルド成功。

## 運用上の影響と検証範囲

現在の14件はすべて未確認であるため、利用者がプロフィールの「緊急連絡先」で内容を確認して「保存する」を押すまで、今後の契約相手には表示されない。登録・変更は引き続き任意。

本番に作業中の契約が0件のため、作業中の未確認拒否・確認済み表示の前後比較は合成データで検証した。本番利用者の契約状態や連絡先を検証のために変更していない。実利用者のログインを用いた本番画面の操作確認は含まない。すでに受信された情報を回収する修正ではなく、過去の第三者による取得の有無を判定したものでもない。
