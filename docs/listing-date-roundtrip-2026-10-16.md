# 求人日程の保存・復元の修正

2026-10-16。入力情報の保存経路を整理した結果、最初に再現できたデータ変換の不一致を修正する。

## 原因と変更

DBの `date_start` / `date_end` とカレンダーのコピー指定は `YYYY-MM-DD`。これを `new Date(value)` で読むとUTCの時刻になり、UTC−3では `2026-12-01` が画面と再保存時に `2026-11-30` へ変わる。また、端末のフォームは `toISOString()`、送信payloadは日付文字列だったため、同じ日程に二つの保存表現が存在していた。

`src/lib/calendarDate.js` に日付の変換を集約し、DB・カレンダーからの入力と端末下書きの保存を日付文字列に統一する。DateはカレンダーUIの境界でのみ使う。不正な日付を翌月へ繰り上げて保存しない。

旧端末下書きの時刻付き文字列は、同時保存された最新payloadの日付から復元する。pendingやbaseは古い入力を含むため使わない。現在のフォームが日付文字列、または日付を消した状態なら、それを優先する。送信payloadの無い旧匿名下書きは保存元の時差を復元できないので、従来の読み方を維持する。すでに誤った日付がDBへ保存された求人を推測で一括修正しない。

## 検証

- 修正前: `TZ=Etc/GMT+3 node --test scripts/device-drafts-ui.test.mjs` がコピー日程の12/1表示で失敗。
- 修正後: 同じ実コンポーネント試験が日本時間・UTC−3で通過。DB編集、コピー、端末保存、オフライン再開、旧ISO下書き移行、公開時の開始日・終了日・休日を照合。
- 日付の保存と復元、年境界、うるう年、夏時間境界、不正値、旧形式との互換を5地域で検証。`calendar-date.test.mjs` をcriticalテストに追加。
- `npm run build`: critical 288件通過、ESLintと本番ビルド成功。通常保存、応答紛失の同一リクエスト再送、競合時の入力保持・上書き防止を既存試験で再確認。

DBスキーマ、RPC、認証・所有者の制限、掲載条件は変更していない。DB試験はローカルPGlite、画面試験は実コンポーネント＋模擬通信であり、本番・実機2台の検証を代替するものではない。
