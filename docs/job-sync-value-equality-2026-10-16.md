# 求人同期の値比較修正

確認日：2026-10-16（日本時間）。PR #8の後続。対象は再送・競合判定のみ。本番DB・main・公開範囲は変更していない。

## 解消した原因

| 原因 | 影響 | 修正 |
|---|---|---|
| 同意時刻の文字列表現をそのまま比較 | 同一時刻でもUTC/JST、小数秒の表記差により再送・比較元照合が競合になる | DBは`work_video_consent_at`だけを`timestamptz`へ変換して比較。端末は明示された時差を解釈し、マイクロ秒まで一致を確認 |
| 再送判定にJSON包含演算子`@>`を使用 | 写真の削除・順序変更等まで「既に保存済み」と誤認し、変更せず成功を返す | 送信されたキーごとにJSON値を完全比較。配列の順序・要素数・入れ子の欠落も区別 |

変更ファイル：`src/lib/jobDraftProtocol.js`と`supabase/migrations/20261018142041_job_sync_value_equality.sql`。テストとCI・説明書は補助変更。

日付だけの値・時差なしの時刻・不正日付を、端末が推測で同一時刻と扱うことはしない。1マイクロ秒違う値も別とする。通常の文字列、NULL、配列の比較を時刻扱いに広げない。

## 維持した安全条件

- 本人の求人だけを操作する。認証・同意版・許可列・RLS・行ロックを変更しない。
- 比較元が古く、送信内容とも一致しなければ競合として拒否する。端末入力を残し、自動上書きしない。
- 公開中の実更新は既存の`update_my_open_job`を通す。応募者ありの更新制限を残す。
- 既存RPCの`SECURITY INVOKER/DEFINER`、`search_path`、実行権限を維持する。新しい公開RPC・テーブル・列を追加しない。
- 移行SQLは現行関数の比較箇所だけを置換する。`draft_step_id`など後から追加された許可列を消さない。
- 置換箇所が想定と異なる場合は例外で停止。1個のDO文内で両関数を変更するため、一方だけ更新された状態を残さない。再実行時は完成形を検査して何もしない。

## 検証

修正前：時刻再送・端末側比較・下書きと公開中の写真並べ替えの回帰試験が失敗。旧包含式が`photos:["a","b"]`に対する`photos:[]`を一致と判定することもローカルDBで確認。

修正後：

- 下書き／公開中 × UTC／日本時間／UTC−3で、初回保存、応答紛失後の再送、表記だけが違う比較元、真の時刻変更を確認。
- 写真・休日・待遇・危険箇所・危険作業の5配列について、削除、空配列、重複数、入れ子の欠落を検査。写真は順序変更も検査。返り値だけでなくDBの保存値を照合。
- 実際の`offlineSync`と`deviceDrafts`をローカルPGliteのSQLへ接続。保存後に応答だけを失わせ、同じUUID・同じリクエストで回復し、1行だけが存在することを確認。
- 独立した2つの端末ストレージを模擬し、Aの保存後に古いBの保存を拒否。Bの入力を保持し、押し直しでもAを上書きしないことを確認。
- 未ログイン・別アカウント・古い同意・禁止列・応募者あり更新の拒否を継続検証。移行前後の関数権限を照合。
- 移行SQLの再実行と、想定外の定義を検知して両関数が変更前のまま残ることを確認。

全体：`TZ=Asia/Tokyo npm run build`成功。critical試験319件通過、失敗0・TODO 0。ESLintはエラー0・既存警告19、本番用Vite/PWAビルド成功。従来TODOだった動画同意時刻の再送を通常の合格必須テストへ変更した。

これはローカルSQL・模擬通信・模擬端末の結果である。実機2台、Supabase経由の通信、本番の全制約・トリガーを含む結合試験は未実施。PGliteのfixtureは本番の完全複製ではない。

## 本番反映前の手順

1. PR #7 → #8 → この修正の依存順を守る。統合先が変わったら差分と全体試験を再確認する。まだマージしない。
2. 本番とは別の検証用DB・アカウントを用意する。Previewの接続先が本番でないことを確認する。本人のログインが必要なら本人に操作を依頼する。
3. 対象DBの2関数定義・権限・RLS・関連制約を読み取り保存する。SupabaseのセキュリティAdvisorを実行し、今回の変更による指摘がないことを確認する。
4. 検証DBにこの1件の移行SQLを適用し、実端末2台で通常保存・応答紛失・同一項目競合を確認する。動画あり／なし、写真削除・並べ替え、オフライン再開も含める。
5. 本番適用は別途承認後。DB修正は旧クライアントとも互換なので、DB適用・確認後にクライアントを反映する。未確認の他の移行SQLをまとめて適用しない。
6. 異常時はクライアントを直前の正常版へ切り戻す。DBも戻す必要がある場合だけ、適用前に保存した2関数定義を復元する。求人データは削除・巻き戻ししない。戻すと今回の既存不具合も再発する点に注意する。
