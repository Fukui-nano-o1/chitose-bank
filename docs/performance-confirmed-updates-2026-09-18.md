# 保存後の反映と用件一覧の取得（2026-09-18）

保存成功後の表示更新と、採用・評価などの用件一覧の取得を改善した。比較元は main `50463d2a714c4c3c541bf75bda00ad7dc8b90eae`。実際のReactコンポーネントと通信を制御した検証で、不要な待ちを減らせたことを確認した。実機で何秒短縮できるか、全画面が瞬時に表示されるかは確認できません。

今回の考え方は、必要なデータだけを取得し、独立した補助情報で表示を止めず、古い応答を無視すること。応答が送信順に返るとは限らないため、画面離脱のキャンセルに加えて、保存成功時にも以前の取得結果を無効にする。[React公式のデータ取得と競合対策](https://react.dev/reference/react/useEffect#fetching-data-with-effects)（2026-09-18確認）。

| 対象 | 変更前 | 変更後 |
| --- | --- | --- |
| 採用・評価・日報・保険などの親画面 | 予定、用件、プロフィール等7種類の取得完了を待つ | 用件一覧1種類で表示を開始 |
| 緊急連絡の親画面 | 7種類の取得完了を待つ | 5種類を取得。予定と採用確認の2種類で一覧を表示し、役割タブの補助3種類は後から反映 |
| 日程変更が成功した直後 | 予定全体の再取得後に移動先を表示 | 成功応答と手元の日程が整合する場合は先に移動先を表示し、裏で再取得 |
| 保存成功後の再取得開始 | 通常の5秒間隔制限に従う | 成功専用通知の初回は待ち時間を挟まない |
| 短時間の保存成功通知 | 通常通知と同じ扱い | 最初の取得＋100ms後の後追いにまとめる |
| 保存前に始まった取得 | 古い一覧が完了済みの用件を戻す場合がある | 保存成功前に始まった取得は反映しない |

7→1、7→5は `TodayPage` 自身が行うデータ取得の数であり、認証セッション取得・子パネルの画像や求人詳細の取得は含まない。7回直列だったという意味でもない。変更前も並行取得だったが、全件の完了をまとめて待っていた。プロフィールの未入力数を `today:unset` に書く処理は現在の読み手がないため、用件画面から取り除いた。

保存成功専用の通知は、カレンダーの日程変更、用件画面からの採用・働き手の評価・保険報告、応募者画面からの採用に接続した。既存のRealtime・復帰・ポーリングは従来の5秒間隔を維持する。非表示の画面では取得せず、復帰時に保留分を処理する。100msは短時間に重なった通知をまとめる間隔であり、APIの応答時間や描画時間を含む実機速度ではない。

日程変更は `move_job_dates` の成功後にだけ反映する。既存SQLに定義された戻り値 `date_start`、`date_end`、`delta_days` を検証し、手元の開始日・終了日から同じ移動と確認できる場合に限って、自分の求人の表示とキャッシュを更新する。サーバーが拒否した場合、戻り値が不足する場合、手元の日程と合わない場合は先行反映しない。応募の合意日・過去の応募記録を移動する処理は追加していない。

既存RPCは休日の最新配列を返さない。休日はキャッシュの配列をDBと同じ移動日数だけずらして表示し、後続の `get_my_calendar_jobs` の結果を優先する。これは最新の休日を保存応答だけで確認したという意味ではない。別の操作で休日が変わっていれば、再取得で表示を訂正する。SQL・DB権限・保存条件は変更していない。既存RPCの呼び出し形式は [Supabase JavaScript rpc](https://supabase.com/docs/reference/javascript/rpc)（2026-09-18確認）に従う。SupabaseのMarkdown形式の変更履歴は取得できなかった。

用件取得の失敗時は既存の一覧を保つ。初回に失敗して何も表示できない場合は「用事なし」とせず、再読み込みを出す。カレンダーキャッシュだけが存在しても、用件一覧を取得済みとは扱わない。保存直前の応答・別の用件画面の応答・離脱後の応答が表示や共有キャッシュを戻さないようにした。日程変更の連続タップは、Reactの次の描画を待たずに送信を止める。

検証結果は次のとおり。通信はすべて代替し、実アカウントへのログイン、本番データの書き込み、メッセージの実送信はしていない。
