# 補助機能の失敗と会員登録・ログインの分離（2026-10-27）

## 目的と確認できた問題

Service Workerの登録成功を会員登録・ログインの開始条件にしない。認証・本人情報の保存・登録許可の確認は必須として維持する。

既存の `public/registerSW.js` は、非対応環境や登録APIの同期例外・Promise拒否を処理し、アプリの認証処理と独立していた。一方、次の経路が残っていた。

1. `index.html` のスクリプト読込エラー監視が、補助用の `registerSW.js` の読込失敗にも反応し、キャッシュ整理と全画面再読み込みを始めていた。合成イベントによる検証で、1回の補助スクリプト読込失敗から1回の全画面再読み込みと復旧フラグの消費を再現した。
2. アプリ本体のスクリプト読込失敗時、Service WorkerやCacheStorageの後片付けが応答しないと、再読み込みまで待ち続けていた。
3. 通常起動時の旧ページキャッシュ削除に付いた `finally` が、削除の拒否を未処理Promiseとして残し、削除に失敗しても完了フラグを保存していた。

上記はコードと合成環境で確認した経路。既報のService Worker登録拒否4件が、このスクリプト読込失敗で起きたと判定したものではない。

## 変更

- 同一オリジンの `/registerSW.js` の読込失敗は、ページ全体の復旧再読み込みを起動しない。入力中の認証コードやフォームを中断しない。
- アプリ本体の必須スクリプトが読めない場合の復旧は維持し、補助APIの後片付け待ちに2秒のタイマーを設けた。遅れて完了しても再読み込みは1回だけ。既存のセッション単位の再読み込み回数制限も維持する。
- 旧キャッシュ整理を `clearLegacyPageCache` にまとめ、起動側は完了を待たない。拒否は関数内で処理し、削除を確認してから完了フラグを付ける。認証情報と入力下書きには触れない。
- これらのファイル・認証UIが変わった際に、GitHub Actionsでも回帰検証を実行する。

認証設定、登録許可、DBスキーマ、RLS、メール送信経路は変更していない。補助機能が失敗しても、認証や保存の失敗を成功扱いにしない。

## 故障を注入したUI検証

実際の `LoginScreen`・`AccountHolderForm` とSupabase SDKをViteで組み立て、JSDOM上で入力・クリックする。API・住所検索は合成データで応答し、外部ネットワークは使用しない。実際の利用者・認証コード・メール送信・本番DBへの書き込みは使用していない。

| --- | --- | --- | --- |
| Service Worker非対応 | 成功 | 成功 | 成功 |

| 補助スクリプトの読込失敗 | 成功 | 成功 | 成功 |

8状態×3経路＝24組合せを確認。処理完了だけでなく、入力保持、不要な再読み込み・二重送信・余計なメール送信がないこと、`serviceWorker.ready` を認証の待ち条件にしないことを確認する。

失敗を正しく止める検証も追加した。誤ったパスワード・無効なOTPではログインしない。保存が拒否されたら入力を保って完了させず、再試行で保存を確認してから完了する。登録許可がない場合は、補助機能の失敗を理由に登録を許可しない。

低水準の復旧処理では、補助スクリプトの失敗を無視した後でも必須スクリプトの復旧が使えること、2秒のタイマー、遅延応答と再読み込みの重複防止、旧キャッシュ整理の拒否・例外を検証する。

2026-10-27の結果：関連55件成功。全体869件成功、ESLintエラー0（変更箇所以外の既存警告19件）、Vite/PWAビルド成功。

実行コマンド：

```sh
node --test scripts/auth-ui.test.mjs scripts/service-worker-registration.test.mjs scripts/account-save-ui.test.mjs
npm run build
```

## 検証範囲の限界

ブラウザAPIの故障は合成環境で注入したもので、実機iPhone・Androidの操作や実メールの到達を確認したものではない。認証サービス停止、端末の通信断、ユーザーによる画面終了、Google翻訳によるDOM変更、全ての補助機能の故障まで成功を保証するものではない。

合格条件は、今回検証した補助機能の失敗が、正常な認証と保存の流れを中断しないこと。会員登録そのものの成功率100％を意味しない。
